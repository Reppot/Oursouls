# Our Souls 2D Storefront Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement this plan task-by-task in the current chat. No additional subagents are required. Checkboxes track execution; this document itself does not claim implementation.

**Goal:** Перевести публичный магазин на качественную фотографическую 2D-графику, заменить главную подборку на интерактивную вешалку и довести каталог, редактор, заказ и админку до общего согласованного сценария.

**Architecture:** Сохранить Flask/Jinja и Supabase; вешалку и новый Canvas 2D-редактор подключать как небольшие независимые дополнения. Структуру проекта отделить от отрисовки, исходные принты и черновики хранить в IndexedDB, готовые товары проверять сервером. Three.js/GLB убрать из публичных зависимостей, старые реализации оставить доступными в истории Git.

**Tech Stack:** Python, Flask, Jinja, Pillow, SQLite для локальной проверки, Supabase для текущих данных/фото, нативные CSS/JavaScript/Canvas 2D/IndexedDB. Не вводить React, платный API или библиотеку карусели.

**Spec:** [Полная спецификация](../specs/2026-11-14-2d-storefront-redesign.md).

## Global Constraints

- Цены не придумываем и массово не заполняем. Для неизвестной цены показываем «Цена по запросу».
- Оформление остаётся через Telegram. Платёжный сервис и бот не подключаются.
- Используем существующее бесплатное размещение. Дополнительные платные API и подписки не нужны.
- Сохраняем десять принтов суммарно на переде и спине, загрузку PNG/JPEG, HEX/RGB/палитру, градиенты и текущие эффекты.
- Личные фото примерки обрабатываются локально, исключаются из архива заказа и автосохранения, очищаются при закрытии примерочной.
- Не меняем содержание принтов, включая ненормативную лексику.
- Публичные главная, конструктор и примерочная работают без Three.js, WebGL, GLB и модели 3D-человека.
- Сохраняем текущие URL, существующие карточки, их изображения, авторизацию, CSRF и фактические `fit_measurements`.
- Не возвращать скрытые товары через seed или устаревшую копию при подтверждении заказа.

## Review Focus

1. Каталожный принт содержит белые/мелкие элементы: смена ткани не перекрашивает и не стирает их — задачи 2, 5, 7.
2. На телефоне пользователь листает вещи и прокручивает страницу: нет перехвата вертикального жеста — задачи 5, 10, 14.
3. Десять больших фото, обновление страницы и отказ IndexedDB: нет потери исходников без сообщения и зависания вкладки — задачи 6–8, 11.
4. Администратор скрывает вариант, пока покупатель оформляет старую корзину: сервер не подтверждает устаревший вариант — задачи 3, 4, 11, 12.
5. Подготовка ZIP завершилась, но браузер запретил скачивание/буфер: проект сохранён, доступны явная ссылка и текст — задачи 9, 11, 14.

## Контракты данных

### Карточка и варианты

Сохранить существующие верхнеуровневые `id`, `slug`, `price`, `sale_price`, `published`, `available`, `images`, `position`, `fit_measurements`. Добавить `schema_version=2`, `garment_type`, `material`, `care`, `variants`, `home_featured`, `home_position`.

`Variant`: `id: str`, `color_name: str`, `color_hex: str | null`, `sizes: list[str]`, `availability: 'in_stock' | 'on_request' | 'unavailable'`, `images: {front: str, back: str | null, details: list[str]}`, `rack_image: str | null`.

`normalize_product(doc: dict) -> dict` создаёт для старой карточки один вариант `legacy-<id>` с фактическим основным фото и цветом; размеры прежнего сценария маркируются как согласуемые, без обещания складского остатка. `validate_variant_selection(product: dict, variant_id: str, size: str) -> dict` возвращает только действующий опубликованный/заказываемый вариант или бросает контролируемую ошибку. Не принимать произвольный цвет из общего справочника.

### Дизайн

`DesignDocument`: `version: 7`, `id`, `templateId`, `templateVersion`, `garmentId`, `colorHex`, `size`, `quantity`, `comment`, `activeSide`, `layers: {front: Layer[], back: Layer[]}`.

`Layer`: `id`, `assetId`, `name`, `cx`, `cy`, `width`, `height`, `rotation`, `flipX`, `flipY`, `effects`. Геометрия нормализована к логической сцене 600 × 700; порядок массива — порядок наложения. Состояние не содержит DOM, canvas, Image или личного фото.

`AssetRecord`: `id`, `fileName`, `mime`, `sourceBlob`, `sourceWidth`, `sourceHeight`. Превью/обработанные холсты — освобождаемые кеши вне документа.

`createDesign(templateId: string): DesignDocument`; `reduceDesign(doc, action): DesignDocument`; `validateDesign(doc, assets): ValidationIssue[]`; `migrateV6(order, assets): DesignDocument`. Для v6 `cx=x/600`, `cy=y/700`; размеры вычисляются из старого `scale` и отношения сторон, эффекты сохраняются.

### 2D-отображение и экспорт

`createRenderer(canvas, manifest): {render(doc, assets, options), exportSide(doc, assets, side, options), hitTest(point, doc, assets), dispose()}`. `options` разделяют направляющие редактора, фотографическое освещение и чистые файлы принтов.

`DraftStore`: `save(doc, assets): Promise<void>`, `load(id): Promise<{doc, assets} | null>`, `list(): Promise<Summary[]>`, `delete(id): Promise<void>`; версия БД мигрируется без удаления старых записей.

`buildOrder({readyItems, designs, assets}): Promise<Blob>` использует текущий `createArchive(files)` и формирует `order.json`, `order.txt`, изображения и исходники. `importDesignArchive(blob): Promise<{doc, assets}>` принимает только известные версии и ограниченный состав.
